# I18N-3

**I18N-3** — Three of the five locales are English. Owner: Implementer.
Priority: **P1.** Measured 2026-08-21 on `origin/master`, by comparing leaf string values key by key
against `messages/en.json` (5,500 keys).

| Locale | Keys  | Identical to English | Reading                     |
| ------ | ----- | -------------------- | --------------------------- |
| `tr`   | 5,500 | 562 (**10%**)        | genuinely translated        |
| `de`   | 5,501 | 5,233 (**95%**)      | English with ~5% translated |
| `fr`   | 5,501 | 5,250 (**95%**)      | English with ~5% translated |
| `ru`   | 5,501 | 5,242 (**95%**)      | English with ~5% translated |

`ru.json` contains **zero Cyrillic characters**. Whatever Russian it once held is gone; what remains is
English plus fragments carrying Turkish diacritics.

`CLAUDE.md` states that public-facing pages require all five languages. A visitor selecting Deutsch,
Français or Русский today gets English with a handful of translated strings — and in the Russian case,
a language selector offering a language the file cannot render.

**This is worse than an untranslated site.** An English-only site is honest about its reach; a language
switcher that returns English is a claim that does not hold, on a project whose subject is claims that
do not hold. It is also the kind of thing a first external reviewer notices in under a minute.

**The three files also carry a UTF-8 BOM** (`en` and `tr` do not), which is `HYG-4`'s defect: they fail
a strict JSON parse and only load through a BOM-tolerant reader. Whatever wrote them used the
PowerShell path `HYG-4` documents.

## Required work

**1. Decide the honest scope first, and say it out loud.** Either translate `de`, `fr` and `ru`
properly, or reduce the published locale list to what actually exists — English and Turkish — and
remove the other three from the switcher until they are real. **Removing a language is not a
regression; advertising one that does not exist is.** This is a Founder call on reach, and either
answer is defensible.

**2. Strip the BOM** from whichever files remain, and fix the write path per `HYG-4`.

**3. Enforcer (Doctrine #047).** Extend the existing `scripts/check-i18n.mjs`: a locale whose values
are more than a set fraction identical to English fails, ratcheted with a baseline so adopting the rule
does not turn CI red on day one. Without it, a partially translated file looks complete to every
existing check — which is exactly how this survived to be found by a value-by-value comparison rather
than by the key-parity check that already runs.

## Acceptance

- Published locales match locales that are actually translated
- No `messages/*.json` carries a BOM
- `check-i18n.mjs` fails a locale that is predominantly English, with a negative test

## Decision taken and landed (2026-08-21, `f88dcf99`)

The Founder chose subtraction. `SUPPORTED_LOCALES` is now `["en", "tr"]`
(`src/lib/constants/index.ts:13`), and `src/i18n/routing.ts:16` derives its locale list from it.
`npx tsc --noEmit` exits 0. The language switcher needed no change — it already filters
`LOCALE_OPTIONS` through `SUPPORTED_LOCALES` (`language-switcher.tsx:22`), so the three removed
languages disappeared from the UI on their own, and the sitemap shrank the same way.

## Three pieces of follow-through, measured after the change

**1. `scripts/check-i18n.mjs` now throws.** Line 69 still hardcodes
`["en", "tr", "de", "fr", "ru"]`, and line 75 does `JSON.parse(readFileSync(p, "utf-8"))` — but
`de`, `fr` and `ru` carry a BOM, so the parse fails with `"abou"... is not valid JSON` and the script
exits 1 on an unhandled exception. **The i18n gate is red right now**, and it is red for a file nobody
serves any more. Fix both halves: drive `publicLangs` from `SUPPORTED_LOCALES` instead of a literal,
and strip the BOM on read (`replace(/^﻿/, "")`) so a stray BOM is a finding rather than a crash.

**2. `src/components/seo/json-ld.tsx:73` still declares `inLanguage: ["en", "tr", "de", "fr", "ru"]`.**
Lines 142 and 224 in the same file already say `["en", "tr"]`, so the file contradicts itself, and the
one that is wrong is the one search engines read as a claim about what this site offers. Derive it from
`SUPPORTED_LOCALES` rather than fixing the literal.

**3. `/de`, `/fr` and `/ru` URLs now 404.** Anything indexed or linked under those prefixes was
serving English yesterday and returns nothing today. Add permanent redirects to the `/en` equivalent in
`next.config.mjs` — `source: "/de/:path*"` → `destination: "/en/:path*"`, and the same for `fr` and
`ru`. Removing a language should cost a visitor a redirect, not a dead end.

Four page components still branch on `locale === "de"` and similar. Those are unreachable now and
harmless; clean them when convenient.

## Closed 2026-08-21 (v13.80) — verified on origin at `2fe485ca`

`scripts/check-i18n.mjs` exits 0, strips the BOM on read and drives its locale list from the published
set. `src/components/seo/json-ld.tsx` derives all three `inLanguage` values from `SUPPORTED_LOCALES`.
`next.config.mjs` permanently redirects both `/de` and `/de/:path*` (and `fr`, `ru`) to the `/en`
equivalent. `npx tsc --noEmit` exits 0.
