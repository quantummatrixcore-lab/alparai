# v13.47 — The agent command hierarchy, and what "alignment" can actually measure

Architect specification, 2026-08-17, answering the Founder Directive of 15 Aug 2026
(`docs/plan/v13.x.md`, archived §11).

## 1. What the Founder asked for

Not a chat product. A **command hierarchy** for the admin panel: Atatürk at the top, receiving a
task, deciding which specialist it belongs to, and dispatching it — architecture to Mimar Sinan,
engineering to Tesla, security to Turing, interface to Da Vinci. Internal, admin-gated, not public.

This is a routing problem with persona-labelled specialist roles. It is not impersonation for
consumption, and the earlier objection on those grounds does not apply to this design.

`bilge-kurul` is the right base — it already carries working specialist prompts and the parallel
dispatch pattern.

## 3. Proposed hierarchy

One file, `.agents/hierarchy.json`. Figures bind to **existing** role prompts; no new prompt text
is invented where a role file already exists.

| Tier | Figure              | Domain                                                       | Bound to                                                     |
| ---- | ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 0    | Atatürk             | Command: classify the task, dispatch, synthesise the replies | `.agents/personas/ceo.md` (rename the role, keep the prompt) |
| 1    | Mimar Sinan         | Architecture, system structure, migrations                   | new — no existing file                                       |
| 1    | Nikola Tesla        | Engineering, performance, data flow, memory                  | `bilge-kurul` §1                                             |
| 1    | Alan Turing         | Security, auth, RLS, cryptography, edge cases                | `bilge-kurul` §3                                             |
| 1    | Leonardo da Vinci   | UI/UX, accessibility, design                                 | `bilge-kurul` §4                                             |
| 1    | Albert Einstein     | Algorithmic complexity, optimisation                         | `bilge-kurul` §2                                             |
| 1    | Fatih Sultan Mehmet | Strategy, market, go-to-market                               | new — no existing file                                       |

Dispatch is **classification, not intelligence**: a keyword/domain map is sufficient for v1 and
costs nothing. An LLM classifier is a later optimisation, only if the map measurably misroutes.

## 4. Two delivery paths

**CLI, available today.** `.claude/skills/` is the only directory Claude Code loads, and it holds
`tom` alone — `bilge-kurul` and `graphify` are in `.agents/skills/` and never load. Copying them
across makes the council usable in a local session immediately, with no code written (`SKILL-1`).
This also repairs `CLAUDE.md` standing rule 2, which instructs every session to use `graphify` for
architecture questions while `graphify` is unwired.

**Admin panel, real work.** Running agents server-side from a web UI needs an admin API route,
server-side model calls, and a job queue. The queue half already exists and works:
`src/lib/autopilot/` (12 files: `worker`, `queue`, `persistence`, `policies`, `budget`, `breaker`,
`retry`, `idempotency`, `telemetry`), with 15 product files already depending on it. Build on it;
do not add a second queue.

Placement constraint: the route belongs under `/api/admin/`, never `/api/v1/` — the latter is the
public API surface, and an admin-gated page in front of a public endpoint is not a gate.

## 5. What "alignment percentage" can and cannot measure

The Founder's objection is correct: writing "you are Atatürk" above a prompt does not produce
Atatürk's judgement, and an agent whose fidelity is unmeasured is decoration.

**What cannot be done.** "This agent is 95% Atatürk" is not measurable. There is no ground truth to
score against — no held-out set of what Atatürk would have said about a Next.js migration. Any such
number is generated, not measured. Publishing one would be the same practice ALPAR AI argues against
in public: a score with an unpublished error rate presented as evidence. The figures proposed in the
Founder Directive reply ("currently 70-80%, raise to 95%+") are `ölçülmedi` and must not enter this
repository, a deck, or a press answer as if measured.

**What can be done — source grounding.** Fix an evaluation set of questions in the figure's actual
domain. For each answer, measure the share of substantive assertions that cite a documented source —
_Nutuk_, recorded decisions, published works, verifiable biography — versus assertions produced from
the model's own fluency. Report the rate **with the evaluation set and the failure cases published**,
so the number is falsifiable by anyone who disagrees with it.

This measures the question actually worth asking: is the agent reasoning from the record, or
improvising in a voice? It is honest, it is cheap, and — unlike a similarity score — it is the kind
of measurement ALPAR AI can defend in public without contradicting its own position.

**Scope note.** Grounding is worth building for the figures where a documented corpus exists. For
Tesla-as-code-reviewer the persona is a labelling convenience with no factual claim attached, and
measuring "Tesla-ness" there would be theatre. Measure where there is something to measure.

## 6. Out of scope

`docs/PROPOSALS/015-ataturk-digital-twin.md` — the Founder's own proposal for a full Atatürk digital
twin (10-agent swarm, _Nutuk_ corpus, GraphRAG, contradiction detection) — states that it "should
likely be orchestrated in an isolated environment or a dedicated sub-module (`Ataturk-Twin`) outside
the primary B2B accountability codebase." That judgement is correct and this specification does not
override it. What is described here is an internal dispatcher for development work, not that
project.
