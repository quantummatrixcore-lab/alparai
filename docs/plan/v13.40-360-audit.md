# v13.40 — 360° audit of the live tree

Architect-directed audit, 2026-08-14, against `master` at `e28c0bfb`.

## Method

Four subagents ran read-only and in parallel over disjoint scopes: security posture, CI and
enforcement layer, record integrity, public surface. Each was launched with the working tree
mistakenly checked out on `claude/strategy-brief-review-i93xcv` — 68 commits behind `master`
and carrying nothing of its own — and each was corrected mid-run and told to discard and
re-measure. That correction is recorded because it is the exact failure mode this project
keeps repeating: a measurement taken against a tree nobody ships.

Three agents were sent back a second time. Two reported conclusions their method did not
support, and one answered a different question than the one asked. Those corrections are
noted per finding. Every figure below cites the command that produced it; anything not
established is marked `ölçülmedi` rather than estimated.

## 1. The `IS_PLAYWRIGHT_TEST` bypass is not contained — and the record said it was

`src/lib/auth/session.ts:14` returns a synthetic user with `role: "admin"` whenever
`IS_PLAYWRIGHT_TEST === "true"`. **There is no `NODE_ENV` condition on that branch**, at the
branch, at module scope, or on the returned value.

The guard everyone believed in is at `src/middleware.ts:54`, and it is real — but it is on the
wrong layer twice over. It is scoped to admin _page_ paths, and it explicitly excludes
`/api/`. All twelve routes under `src/app/api/admin/**` call `getCurrentUser()` directly and
never traverse it. `src/actions/incidents.ts:466` carries the same unguarded pattern, short-
circuiting `submitIncident` to a mock return.

Nothing in the repository throws, asserts, or fails a build when `IS_PLAYWRIGHT_TEST` is
truthy while `NODE_ENV === "production"`. The application starts and serves with full
authentication bypass.

**Severity, stated precisely.** This is not remotely exploitable: an attacker cannot set the
variable. It is a latent configuration defect, one wrong deployment environment away from
total administrative compromise, with no tripwire. What makes it worth the top of this list is
not the likelihood — it is that the mitigation the project believed was in place does not
cover the code path that matters, so the risk was carried as closed.

**Fix (Implementer, `src/**` — not patched here because there is no live exposure):** wrap the
`session.ts:14` branch and the `incidents.ts:466` branch in `process.env.NODE_ENV !==
"production"`, and add a module-scope throw when both conditions hold. The throw is the part
that matters — a guard that silently degrades is how this defect survived.

## 2. `api_keys` stores provider secrets in plaintext

`supabase/migrations/20260623000200_create_api_keys_table.sql:2-5` defines
`api_key text NOT NULL`. Provider credentials are stored unencrypted at the application layer.

The table's RLS policy (same file, lines 10-20) restricts access to `authenticated` users
holding `role = 'admin'` or `'ceo'`, and that policy is correctly written. But it authorises on
role, and the synthetic user from finding 1 carries `role: "admin"` — so the two defects
compose: the environment variable that grants fake admin also satisfies the policy protecting
every provider key in cleartext.

`ölçülmedi`: whether Supabase's storage-layer encryption-at-rest is enabled on this project.
That is a dashboard setting, not a repository fact, and was not verifiable from here.

Verified directly on runs `31750260782` and `31750959708`: all four jobs in each carried

This supersedes the earlier record of "29 of 30 affected". The correct statement is that the

could not reach that API. Until it is known, no branch-protection claim should be recorded.

## 5. v13.37's enforcer count does not describe `master`

v13.37 recorded 13 enforcer scripts with 3 wired to nothing. On `master` there are **10, and
all 10 are wired** — 7 via `ci.yml`, 3 via `master-plan-guard.yml`, 1 via
`masterplan-consistency.yml`, several also via `package.json`. Zero orphaned, zero
referenced-but-missing.

The three "orphaned" scripts — `check-i18n-admin.mjs`, `check-i18n-completeness.mjs`,
`check-keys.mjs` — exist only on the stale Architect branch and have never shipped. The
original finding was taken against a tree that was never deployed, and was then promoted into
doctrine. C-7 exists precisely to catch this and did not fire. The v13.37 measurement should
be marked superseded rather than deleted; the reasoning it supports still holds, the count
does not.

Re-tested this round: all 10 enforcers return 0 on pass and 1 on real failure. No repeat of the
zero-item-parse defect.

163 `closed-by:` occurrences across `docs/MASTER_PLAN.md` and `docs/plan/**`, reconciled:

| Category                                  | Occurrences | Unique |
| ----------------------------------------- | ----------- | ------ |
| Resolve via `git cat-file -e`             | 122         | 63     |
| Non-SHA closure claims — **real defects** | 29          | 21     |

The first pass reported these as 163 / 52 / 26, which does not sum, and counted documentation

inflating the defect count using the specification of the rule as evidence against it.

The 29 real defects cluster in archived version files (`v12.12x.md` especially, with
descriptive slugs like `stripe-webhook-tier` in the SHA position). Only two sit in active item
files: `docs/plan/items/GOV-1.md` and `docs/plan/items/ROUTE-1.md`, both `pending-push`.

**Misattribution: 5 sampled, 0 found, 117 occurrences unexamined.** This is a sample, not a
census, and the earlier "0 misattributed closures" overstated it.

## 7. Board file is at its ceiling

`docs/MASTER_PLAN.md`: **599 lines, 118,167 bytes**, against a 600-line cap in
`scripts/check-master-plan-length.mjs`. One line of headroom.

This is C-8 arriving on schedule: the cap governs lines while cost accrues in bytes, so the
file reached 118 KB in full compliance. Any further section requires compression first. Raising
the cap again is the documented failure, not the fix.

## 9. Two hygiene items, correctly sized

**57 `target="_blank"` anchors across 29 files lack `rel="noopener noreferrer"`.** The auditing
agent classified this as a critical XSS vulnerability. It is neither: the risk is reverse
tabnabbing, and every current browser has applied implicit `rel="noopener"` to
`target="_blank"` since 2021. It is real hygiene debt worth clearing, and it is not critical.
Recording it at the inflated severity would repeat the measurement failure this audit exists to
correct.

**16 files import `Link` from `next/link` rather than `@/i18n/routing`**, against the stated
convention. `check-internal-links.mjs` passes regardless, so locale prefixes are not currently
breaking. Convention drift, not a defect — but the convention has no enforcer, which is the
C-4 state the project has agreed not to leave ambiguous.

## What this audit did not establish

- Required status checks on `master` — the API was unreachable from the auditing agent.
- Misattribution across the 117 unexamined citation occurrences.
- Supabase encryption-at-rest for the `api_keys` table.
- Visibility of the `Alparai.com` repository itself. `quantummatrixcore-lab/alparai` is public
  and `alparai-platform` is private; this repository did not surface in search and its
  visibility is unknown. It determines how much of the `.agents/swarm/` naming is public.
